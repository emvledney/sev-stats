# vhal-properties

## SUMMARY
The core limit is in Google's code: no standard AAOS vehicle property exists for HV pack voltage, pack current, cell voltages, cell or module temperatures, coolant or motor temperatures, amp-hour capacity or state of health. I checked this directly in AOSP main / android-17.0.0_r1 (VehicleProperty.aidl and VehiclePropertyIds.java). The only property that uses an AMPERE unit is EV_CHARGE_CURRENT_DRAW_LIMIT, which is the charger draw-limit setting, not pack current. GM's own vendor properties (group 0x2xxxxxxx) need signature|privileged permissions (CAR_VENDOR_EXTENSION or GET_CAR_VENDOR_CATEGORY_*), so a Play or sideloaded app cannot read them. Cell-level voltages, pack V/I, battery temperatures and Ah therefore cannot come from the head unit. They need a separate read-only OBD/UDS path. On the AAOS side, a third-party app gets the EV basics with runtime ('dangerous') permission android.car.permission.CAR_ENERGY:
- EV_BATTERY_LEVEL (Wh), EV_CURRENT_BATTERY_CAPACITY (Wh, Android 14+) and RANGE_REMAINING (m).
- EV_BATTERY_INSTANTANEOUS_CHARGE_RATE (mW; spec says positive = charging, negative = discharging, which gives pack power in kW).
- EV_CHARGE_STATE, EV_CHARGE_TIME_REMAINING, EV_CHARGE_PERCENT_LIMIT, EV_CHARGE_CURRENT_DRAW_LIMIT and EV_REGENERATIVE_BRAKING_STATE (all Android 13+).

With install-time ('normal') permissions it also gets INFO_EV_BATTERY_CAPACITY (nominal Wh), make/model/year and connector type (CAR_INFO), charge port open/connected (CAR_ENERGY_PORTS), gear, ignition, parking brake, regen level and stopping mode (CAR_POWERTRAIN), outside temperature (CAR_EXTERIOR_ENVIRONMENT) and display units (READ_CAR_DISPLAY_UNITS). Speed and wheel ticks need CAR_SPEED (dangerous). VIN, cabin HVAC temperatures, engine temperatures and curb weight stay signature|privileged on every Android version. Odometer, tire pressure, steering angle and engine RPM only become readable through the new *_3P dangerous permissions on Android 16+.

Which properties exist depends on the head unit's Android version, because the on-device car service only passes through properties it knows. Android 12's car service has no EV_CHARGE_*, EV_CURRENT_BATTERY_CAPACITY or EV_STOPPING_MODE entries. Android 14's car service has those but not EV_BATTERY_AVERAGE_TEMPERATURE, which needs Android 15+ even if GM's VHAL supplies it. GM's published emulator is Android 14 / API 34 on 'VCU1.0' (Cadillac LYRIQ and CELESTIQ images). A 2026 NHTSA OTA bulletin says the 2024 Silverado EV head unit is the 'VCU (Virtual Cockpit Unit)' and received an 'Android update'. Owner forums report Ultium EVs moving from Android 12 to Android 14. So battery temperature is most likely not readable through AAOS on this truck today. The Car App Library's CarInfo is a thin subset built on the same in-process CarPropertyManager, so it grants no extra access. It covers model, energy profile, energy level, speed and EV port status, has no charge rate, temperature or charge state, and on AAOS its CarSensors returns UNIMPLEMENTED. Real-car evidence is thin for GM: the Home Assistant Play app on a GM-built Honda Prologue shows battery level, range and charging status but no odometer. Car Stats Viewer on Polestar/Volvo shows the charge-rate sign works as specified on real cars. No public dump of a GM VHAL property list exists. The first build step should therefore be a read-only property-probe app run on GM's LYRIQ API 34 emulator and then on the truck. For safety, a non-privileged app cannot write any standard vehicle property, because every write permission is signature|privileged in the car service manifest. Two operational risks remain: CarWatchdog disables third-party apps that write more than 3 GiB of disk in the foreground or 2 GiB in the background per day (owners of a Blazer EV and a CT5 report apps being disabled), and the template host throttles screen refresh while driving.

## FINDINGS

### [vp-1] (high, CRITICAL) No standard VHAL / VehiclePropertyIds property exposes HV pack voltage, pack current, per-cell voltages, cell/module temperatures, coolant/motor temperatures, Ah capacity or SoH; cell-level and V/I data cannot come from AAOS APIs.
I compared every @unit annotation in VehicleProperty.aidl (main, which equals android-17.0.0_r1). The only AMPERE property is EV_CHARGE_CURRENT_DRAW_LIMIT (the user charge-current limit). No property uses VOLT or MILLIVOLT. CELSIUS appears only on ENGINE_COOLANT_TEMP, ENGINE_OIL_TEMP, EV_BATTERY_AVERAGE_TEMPERATURE, HVAC_TEMPERATURE_CURRENT/SET and ENV_OUTSIDE_TEMPERATURE. AMPERE_HOURS appears only as a display-unit choice for EV_BATTERY_DISPLAY_UNITS. The property set in Android 17 is identical to Android 16. Any GM-specific BMS signals would be vendor properties (VehiclePropertyGroup VENDOR = 0x20000000), which default to android.car.permission.CAR_VENDOR_EXTENSION (signature|privileged). The plan must therefore use a separate read-only OBD-II/UDS path for cell voltages, pack V/I, temperatures and Ah.

### [vp-2] (high, CRITICAL) Third-party apps can read the core EV energy data with android.car.permission.CAR_ENERGY, a 'dangerous' permission that needs a runtime grant (permission group android.car.permission-group.CAR_MONITORING).
CAR_ENERGY has been protectionLevel=dangerous in the Car service AndroidManifest from Android 10 through main. It gates EV_BATTERY_LEVEL (0x11600309, Wh), EV_CURRENT_BATTERY_CAPACITY (0x1160030D, Wh, API 34), EV_BATTERY_INSTANTANEOUS_CHARGE_RATE (0x1160030C, mW), RANGE_REMAINING (0x11600308, m), EV_CHARGE_STATE (0x11400F41), EV_CHARGE_TIME_REMAINING (0x11400F43, s), EV_CHARGE_PERCENT_LIMIT (0x11600F40), EV_CHARGE_CURRENT_DRAW_LIMIT (0x11600F3F, A), EV_CHARGE_SWITCH (read only) and EV_REGENERATIVE_BRAKING_STATE (0x11400F44), plus EV_BATTERY_AVERAGE_TEMPERATURE on Android 15+. Every corresponding write permission (CONTROL_CAR_ENERGY, ADJUST_RANGE_REMAINING) is signature|privileged.

### [vp-3] (high, CRITICAL) Which properties an app can use is set by the head unit's Android version (the on-device car service), not by the app's SDK. On Android 12, EV_CHARGE_*, EV_CURRENT_BATTERY_CAPACITY, EV_STOPPING_MODE and EV_BRAKE_REGENERATION_LEVEL are absent. On Android 14 those are present but EV_BATTERY_AVERAGE_TEMPERATURE is absent.
In Android 14, PropertyHalServiceIds.isSupportedProperty() returns true only when the property ID is in the service's permission map or is a vendor property, so unknown system properties are dropped even if the OEM VHAL implements them. The 12.1.0_r1 map has no EV_CHARGE_STATE or EV_CURRENT_BATTERY_CAPACITY. The 14.0.0_r1 map has EV_CHARGE_STATE, EV_CURRENT_BATTERY_CAPACITY, EV_CHARGE_* (CAR_ENERGY), EV_STOPPING_MODE and EV_BRAKE_REGENERATION_LEVEL (CAR_POWERTRAIN), but no EV_BATTERY_AVERAGE_TEMPERATURE. That property first appears in android-15.0.0_r1 behind flag android_vic_vehicle_properties, as VHAL AIDL @version 3.

### [vp-5] (medium) EV_BATTERY_INSTANTANEOUS_CHARGE_RATE is the only pack-power signal. It is a Float in milliwatts, CONTINUOUS, with positive = charging and negative = discharging; pack current and voltage cannot be derived from it alone.
Both the VHAL AIDL (@unit VehicleUnit.MILLIWATTS) and VehiclePropertyIds javadoc state this sign convention. Real-car evidence: Car Stats Viewer (Polestar/Volvo) multiplies the raw value by -1 (emulatorPowerSign = -1) and computes consumption = (power/1000)/(speed*3.6) Wh/km. Positive consumption while driving means the raw value is negative when discharging, which matches the spec. Car Stats Viewer also allows power to be null on some device builds ('moose', 'ihu_emulator'), so not every OEM implements this property. GM's implementation and sign are unverified. kW = value/1e6. Current would need pack voltage, which no VHAL property provides.
Sources: https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/automotive/vehicle/aidl_property/android/hardware/automotive/vehicle/VehicleProperty.aidl https://github.com/Ixam97/CarStatsViewer/blob/master/automotive/src/main/java/com/ixam97/carStatsViewer/carPropertiesClient/CarProperties.kt https://github.com/Ixam97/CarStatsViewer/blob/master/automotive/src/main/java/com/ixam97/carStatsViewer/dataProcessor/RealTimeData.kt https://github.com/Ixam97/CarStatsViewer/blob/master/automotive/src/main/java/com/ixam97/carStatsViewer/CarStatsViewer.kt

### [vp-6] (high) Battery capacity in kWh is partly available: INFO_EV_BATTERY_CAPACITY gives nominal Wh when new (CAR_INFO, normal) and EV_CURRENT_BATTERY_CAPACITY gives real-time usable Wh including aging and temperature (CAR_ENERGY, Android 14+). Ah is not available.
SoC% = EV_BATTERY_LEVEL / EV_CURRENT_BATTERY_CAPACITY * 100, per the AOSP javadoc. Fall back to INFO_EV_BATTERY_CAPACITY on Android 12/13. EV_CURRENT_BATTERY_CAPACITY / INFO_EV_BATTERY_CAPACITY is only a rough capacity-fade proxy, because the current value is also temperature-dependent. Ah can only be approximated as Wh / nominal pack voltage, and pack voltage must come from OBD or a hard-coded spec.
Sources: https://android.googlesource.com/platform/packages/services/Car/+/refs/heads/main/car-lib/src/android/car/VehiclePropertyIds.java

### [vp-7] (high) Several properties stay signature|privileged on the head units GM ships, so Play or sideloaded apps cannot read them: INFO_VIN, PERF_ODOMETER (until Android 16), TIRE_PRESSURE (until Android 16), HVAC_TEMPERATURE_CURRENT/SET (cabin temperature), ENGINE_COOLANT_TEMP/OIL_TEMP, ENGINE_RPM (until Android 16), VEHICLE_CURB_WEIGHT, TRAILER_PRESENT, ADAS states, OBD2_LIVE_FRAME and all vendor properties.

### [vp-8] (high) The Car App Library (androidx.car.app.hardware) gives no extra access. On AAOS it calls Car.createCar(context) and CarPropertyManager inside the app's own process, with the app's own permissions, and exposes only a subset of the data.
In androidx-main, PropertyRequestProcessor does Car.createCar(context) and car.getCarManager(Car.PROPERTY_SERVICE). CarInfo covers fetchModel (CAR_INFO), fetchEnergyProfile (CAR_INFO), fetchExteriorDimensions (CAR_INFO, Car App API 7), addEnergyLevelListener (CAR_ENERGY + CAR_ENERGY_PORTS + READ_CAR_DISPLAY_UNITS), addSpeedListener (CAR_SPEED + READ_CAR_DISPLAY_UNITS), addEvStatusListener (port open/connected), addTollListener, and addMileageListener (not available on AAOS from Play). It has no charge rate, battery temperature or charge state. CarSensors returns STATUS_UNIMPLEMENTED on AAOS. CarClimate requires CONTROL_CAR_CLIMATE (signature). The current androidx EnergyLevel computes battery percent only from EV_CURRENT_BATTERY_CAPACITY, so percent is unavailable on Android 12/13 head units. A carlink_native PR (Apr 2026, 2024 Silverado ICE) claimed the templates host proxies access. The androidx source contradicts that claim.

### [vp-11] (high) Sample rates for continuous properties are OEM-defined (CarPropertyConfig min/max sample rate). The AOSP reference VHAL uses EV_BATTERY_INSTANTANEOUS_CHARGE_RATE 1–10 Hz, EV_BATTERY_LEVEL 1–100 Hz, RANGE_REMAINING 1–2 Hz, EV_BATTERY_AVERAGE_TEMPERATURE 1–2 Hz, ENV_OUTSIDE_TEMPERATURE 1–2 Hz and PERF_VEHICLE_SPEED 1–10 Hz.
CarPropertyManager rate constants: SENSOR_RATE_ONCHANGE 0, NORMAL 1, UI 5, FAST 10, FASTEST 100 Hz. Requests are clamped to the property's configured min/max. On Android 12/14 use registerCallback(callback, propId, rateHz). subscribePropertyEvents() with variable update rate is the Android 15+ API (flag VARIABLE_UPDATE_RATE). Car Stats Viewer requests 100 Hz for speed and power on Polestar. GM's real rates are unknown.

### [vp-12] (high) A non-privileged app cannot write any standard vehicle property, because every write/control permission is signature|privileged in the car service manifest. An app that only declares read permissions and never calls setProperty cannot change vehicle behavior through the property API.
Writable properties need CONTROL_CAR_ENERGY, CONTROL_CAR_ENERGY_PORTS, ADJUST_RANGE_REMAINING, CONTROL_CAR_CLIMATE, CONTROL_POWERTRAIN, CONTROL_CAR_HORN and similar, all signature|privileged in the manifest. Display-unit writes need CONTROL_CAR_DISPLAY_UNITS (normal) plus CAR_VENDOR_EXTENSION (signature). One discrepancy: the VehiclePropertyIds javadoc calls CONTROL_CAR_HORN 'Dangerous' for VEHICLE_HORN_ENGAGED, but the manifest declares it signature|privileged, and the manifest is what the system enforces.
Sources: https://android.googlesource.com/platform/packages/services/Car/+/refs/heads/main/service/AndroidManifest.xml https://android.googlesource.com/platform/packages/services/Car/+/refs/heads/main/car-lib/src/android/car/VehiclePropertyIds.java

### [vp-13] (high) CarWatchdog can silently disable a third-party dashboard or logging app that writes too much to disk, and GM owners report Play apps being disabled.
AOSP Watchdog defaults for third-party apps are 3 GiB of writes per day in the foreground, 2 GiB in the background and 4 GiB in garage mode. All third-party apps are 'safe-to-terminate'. On repeated overuse the app is set to COMPONENT_ENABLED_STATE_DISABLED_UNTIL_USED and disappears from the launcher, with a notification offering 'Prioritize app performance'. In HA issue #5418, a 2024 Blazer EV owner's app was disabled after about 24 h and a 2025 CT5 owner's after weeks ('consuming too many resources'). Keep logging writes small and batched.
Sources: https://source.android.com/docs/automotive/watchdog/wd_flash_memory https://github.com/home-assistant/android/issues/5418

### [vp-15] (medium, CRITICAL) There is no way to read battery temperature without OBD on the current (Android 14) GM head unit. The only standard route, EV_BATTERY_AVERAGE_TEMPERATURE (0x1160030E, °C, CAR_ENERGY), needs an Android 15+ car service and GM's VHAL to implement it.

### [vp-16] (high) getPropertyList() returns only properties the app is allowed to access. Unsupported properties throw IllegalArgumentException on subscribe, and missing permissions throw SecurityException. A probe app can therefore map what GM implements.
The CarPropertyManager javadoc says getPropertyList() returns 'the list of properties supported by this car that the application may access'. subscribePropertyEvents and registerCallback document SecurityException for missing read permission and IllegalArgumentException for unsupported properties. CarPropertyValue.getStatus() / PropertyNotAvailableException report temporarily unavailable values. Build setup: useLibrary("android.car") plus <uses-feature android:name="android.hardware.type.automotive" android:required="true"/>, as in Car Stats Viewer's build.gradle.kts and manifest.

- Exact Android version and build on the user's truck (Settings > About). Android 12 vs 14 decides whether EV_CHARGE_*, EV_CURRENT_BATTERY_CAPACITY, EV_STOPPING_MODE and EV_BRAKE_REGENERATION_LEVEL exist at all.
- Which standard properties GM's production VHAL actually populates (especially EV_BATTERY_INSTANTANEOUS_CHARGE_RATE, EV_CURRENT_BATTERY_CAPACITY, EV_CHARGE_STATE, ENV_OUTSIDE_TEMPERATURE), their min/max sample rates, and whether GM keeps the AOSP sign convention for charge rate. No public dump exists.
- Whether GM's LYRIQ API 34 emulator VHAL configuration matches the production Silverado EV VCU property set.
- Whether and when GM will ship Android 15/16 on Ultium VCUs. That would enable EV_BATTERY_AVERAGE_TEMPERATURE and the Android 16 *_3P permissions (odometer, tire pressure, efficiency), if GM enables the flags and the VHAL implements the properties.
- Whether production GM VCUs expose Developer options and adb (USB or Wi-Fi) for sideloading and `pm grant`; third-party vendor pages call GM 'restricted' and I found no first-party confirmation.
- Whether a Play Console Automotive OS internal-testing-track install on a GM vehicle allows a distraction-optimized (non-templated) dashboard activity while driving, as Car Stats Viewer did on Polestar.
- Whether GM's runtime permission dialog for CAR_ENERGY / CAR_SPEED appears normally for internal-test or sideloaded apps (the Home Assistant evidence suggests it does for Play apps).
- Whether the Home Assistant 'battery level' on the Prologue came from EV_CURRENT_BATTERY_CAPACITY or INFO_EV_BATTERY_CAPACITY, which depends on the androidx version that build used.

## RECOMMENDATIONS
- Plan two data sources from the start. The AAOS CarPropertyManager path covers SoC, kW, charge state, range, gear, speed and outside temperature. A separate read-only OBD-II/UDS path is needed for pack voltage and current, cell voltages, temperatures and Ah, because no AAOS API can provide them to a third-party app.
- Build a read-only 'VHAL probe' module first. Setup: useLibrary("android.car") and <uses-feature android:name="android.hardware.type.automotive" android:required="true"/>. Declare only read permissions: CAR_INFO, CAR_ENERGY_PORTS, CAR_POWERTRAIN, CAR_EXTERIOR_ENVIRONMENT, READ_CAR_DISPLAY_UNITS (normal), plus CAR_ENERGY and CAR_SPEED (runtime). Then call getPropertyList(), log each CarPropertyConfig (ID hex, access, changeMode, areaIds, min/max sample rate, configArray), getProperty() every VehiclePropertyIds constant, and log SecurityException, IllegalArgumentException and PropertyNotAvailableException. Never call setProperty and never declare CONTROL_* permissions.
- Run the probe first on GM's emulator. The user should add https://developer.gm.com/v1/android-emulator/repository.xml as an SDK Update Site in Android Studio, accept GM's license themselves, install system-images;android-34;android-automotive-lyriq;x86_64 (about 2.5 GB, about 10 GB disk per AVD) and create an AVD with the 'Cadillac Lyriq display' profile. Then run the probe on the truck. Do not unpack the GM image to read its VHAL config; the license forbids reverse engineering.
- Read data with CarPropertyManager directly rather than CarHardwareManager/CarInfo, which lack charge rate and charge state and compute SoC only from EV_CURRENT_BATTERY_CAPACITY. Compute SoC = EV_BATTERY_LEVEL / (EV_CURRENT_BATTERY_CAPACITY, or else INFO_EV_BATTERY_CAPACITY) and kW = EV_BATTERY_INSTANTANEOUS_CHARGE_RATE / 1e6. Check the sign against a known charging session.
- Subscribe with registerCallback(callback, propId, rate), the API available on Android 12/14. Clamp the rate to config.getMaxSampleRate(), use about 5–10 Hz for power and ON_CHANGE for state properties. Gate subscribePropertyEvents() / variable update rate on SDK >= 35.
- Keep on-device logging lean (for example 1 Hz rows batched into Room) to stay far below CarWatchdog's 2–3 GiB/day write thresholds. Also plan for the app being disabled-until-used: the user re-enables it via the launcher or Play.
- Design the dashboard for driving restrictions.
