### NEW FACTS

- GM production head units do not allow adb install or APK sideloading. The working path is your own Play Console app on a dedicated Android Automotive OS internal-testing track, installed to the car from Google Play's website. This contradicts the user's assumption that adb can be used to install.: OpenAutoLink README: 'Install on a locked GM vehicle through your own Google Play Console app's dedicated Android Automotive OS Internal Test. APK sideloading is not supported on these head units.' and the APK 'cannot be sideloaded onto a locked GM production head unit.'

Steps from docs/install-gm.md:
1. Test and release → Advanced settings → Form factors → + Add form factor → Android Automotive OS → Manage.
2. Select 'Use a dedicated release track for Android Automotive OS' (irreversible), then Save.
3. Test and release → Testing → Internal testing, and choose Android Automotive OS in the form-factor selector.
4. Create new release, upload the signed AAB (Play App Signing), then Start rollout to internal testing.
5. Testers → Create email list with the car's exact Play Store Google account, tick the list, Save.
6. Open the 'Join on web' opt-in link, then Become a tester.
7. On Play's web page choose Install and pick the car in the device picker; the car must be online.
8. Grant car-data permissions on the car under Settings → Apps → <app> → Permissions, while parked.

Internal testing holds up to 100 testers. Google's distribute doc says internal testing gets no form-factor review. Updates need a higher versionCode, the same upload key and the same package name. (https://raw.githubusercontent.com/mossyhub/openautolink/main/README.md https://raw.githubusercontent.com/mossyhub/openautolink/main/docs/install-gm.md https://developer.android.com/training/cars/distribute)

- GM's com.gm.vehicleinfo app exports an unprotected ContentProvider (com.gm.vehicleinfo.HistoryProvider) that any app can query for motor power, motor torque and battery-level time series. A sibling provider accepts writes from any app.: OpenAutoLink's GmHistoryProviderRepository.kt documents the provider:
- Authority com.gm.vehicleinfo.HistoryProvider, paths history/e_power, history/e_torque, history/e_battery, history/ice_power, history/ice_torque.
- Selection args 'SELECTION_HISTORY_DATA' or 'SELECTION_HISTORY_TIMESTAMP'.
- Tables HistoricalData(id, value, history_type) as a 6,000-row ring buffer, and HistoryTimestamp.
- 'no manifest permission and no runtime checkCallingPermission in query()'.

The same audit says EnergyEfficiencyGraphProvider's insert() accepts arbitrary CarPropertyValues from any app.

Plan implications:
- HistoryProvider is an unofficial, read-only source of motor power that GM may close at any time. Using it relies on an apparent GM misconfiguration, which the user should knowingly accept or skip.
- The app must never call insert/update/delete on any GM provider, because that could corrupt GM's on-screen energy data. This is a write vector the 'no setProperty' rule does not cover.
- Neither provider exposes voltages, currents, cell data or temperatures. (https://raw.githubusercontent.com/mossyhub/openautolink/main/app/src/main/java/com/openautolink/app/data/GmHistoryProviderRepository.kt https://raw.githubusercontent.com/mossyhub/openautolink/main/app/src/main/java/com/openautolink/app/diagnostics/GmReconProbe.kt)
