# hardware-connectivity

## SUMMARY
The plan assumes adb installs onto the truck's head unit, and that won't work. GM's Google built-in head units only accept a GM-certificate adb client. Turning on Developer options does not put adb on any user-facing USB port. The community workarounds need a hardware tap and a security change inside the radio, so they break the "no truck impact" rule. What owners actually use, and what works, is the Google Play Console Internal testing track: build an .aab, add yourself as a tester, and install from the car's Play Store. Silverado EV, Sierra EV, Blazer EV and Equinox EV owners all report this working. Only apps installed through Play can keep a distraction-optimized activity on screen while driving. Sideloaded copies are blocked once the truck leaves Park, and Google's own AAOS emulator documentation says the same. The EV head unit (GM/Bosch "VCU" family) is an arm64 Qualcomm unit running AAOS 12L, with Android 14 (API 34) rolling out. Builds must be arm64-v8a or ABI-neutral. GM publishes x86_64 Android 14 emulator images (Lyriq and Celestiq, VCU1.0) through an Android Studio SDK update site. On the vehicle side, the OBD port on GM VIP/Global B is cut off from the internal buses by the K56 serial data gateway. Listening on the port shows no normal vehicle traffic, so every value has to be requested with UDS 0x22 reads. Classic 500 kbit/s 29-bit CAN is enough for the key battery-module (BEC 0xCB) and drive-motor (DMCM 0x17) data IDs on Ultium. Evidence: an ELM327 BLE clone on a BrightDrop Zevo (Coldarn/hacs_gm_ultium), WiCAN's BT1/Sierra EV profiles, and Silverado EV owners reading per-module voltages and temperatures with Car Scanner plus an OBDLink MX+, vLinker MC+ or LELink. CAN FD at the OBD port is claimed only second-hand (5 Mbit/s on the port side), and nothing found shows a needed data ID requiring it. GM's addressing is unusual. Profiles use header 0x14DACBF1, a receive filter of 0x142AF1CB, and user-defined flow control. One project also reports the standard 0x18DACBF1 working. So the adapter must accept custom 29-bit headers, receive filters and flow-control settings. STN-based OBDLink adapters accept all of these and handle messages up to 4 KB, but no ELM or STN adapter supports CAN FD. CAN FD-capable Linux interfaces are PEAK PCAN-USB FD, Kvaser Leaf v3 and comma red panda. The CANable 2.0 hardware supports FD, but its candleLight firmware does not. The laptop's CachyOS 7.2.10 kernel already includes can-isotp, gs_usb, peak_usb, kvaser_usb, slcan and mcp251xfd. python-can and bleak are in Arch extra; can-utils, python-can-isotp, python-udsoncan, savvycan and cangaroo are in the AUR. For the head-unit app link, there is direct evidence for USB and Wi-Fi but not for BLE. USB: a third-party internal-testing app on Silverado EV and Sierra EV talks raw USB through UsbManager. GM asks for USB permission on every attach and has EV-specific device-type quirks. Wi-Fi: Chevrolet officially supports joining outside networks, and Android 10+ apps can request local-only connections, which are auto-approved after the first approval if the exact SSID and BSSID are given. BLE: the radio module supports Classic and LE, and the compatibility rules say automotive units SHOULD support LE. No public report shows a third-party app using BLE GATT on GM's AAOS, so this is the first thing to test. Recommended architecture, in three phases. Phase 1: laptop discovery with SocketCAN and an STN adapter, sending only 0x22 reads. Phase 2: an internal-testing AAOS app talking BLE to an OBDLink CX, or to an ESP32-S3/MCP2518FD bridge that applies a send whitelist and only polls while the truck is awake. Fallbacks are USB-serial and then Wi-Fi (WiCAN Pro or a Pi). The OBD port is always powered and polling keeps modules awake, so every design must stop polling when the truck sleeps. Fallbacks if the in-dash app fails: a phone or tablet with Car Scanner, or WiCAN Pro feeding MQTT/Home Assistant. Phone projection is not an option because the Silverado EV has no Android Auto or CarPlay.

## FINDINGS

### [hw-1] (high, CRITICAL) Owners cannot use adb to install onto the GM Google built-in head unit; the working install path is the Google Play Console Internal testing track.
VERIFIED (community, consistent 2024-2026). Developer options can be turned on, but adb never appears on the user-facing USB ports (Tachi91, 2024-04-21). GM locks adb to its own certificate-based client (2024-07-09). GM's developer portal declined to allow app sideloading for an individual owner (2024-05-13). The adb shell owners have obtained (user 2000) needs a hardware tap on the radio's X8 HSAL-2 USB connector plus a Type-C breakout with 5.1 kOhm Rd, and also needs the GM certificate requirement bypassed through a 'MEC/SBI flip' in the VIP (Renesas RH850) MCU (2026-10-10). GM calibration pushes have started relocking this (2026-01-02). That rules it out under the no-truck-impact constraint. The working path many EV owners report (Silverado EV RST, Sierra EV, Blazer EV, Equinox EV, Optiq) is: compile an .aab, open Play Console (US$25 developer account), Create app, Testing > Internal testing, upload, add your Google account as a tester, accept the opt-in link, then install from the car's Play Store. Example reports: RWerksman 2025-08-12, cybergeek1 2026-01-02, Tachi91 2026-01-03; the Carlink_native README describes the same steps. Inference: the user's laptop will be used for building, CAN discovery and as a temporary bridge, not for adb to the head unit.

### [hw-5] (medium) The OBD port on GM VIP/Global B sits behind the K56 serial data gateway (SDGM), so listening there shows no vehicle broadcast traffic. Every value has to be requested with UDS reads.
VERIFIED (technician write-up): 'VIP SDGM - Complete network isolation'. The SDGM wakes networks on request. High-speed modules reach the OBD port 'through the SDGM at terminals 6 and 14'. Port pin 1 is unused on VIP. '120 Ω will be measured' at pins 6-14 on Gen3 and VIP (versus 60 Ω on older designs), meaning only one terminator on the port side. Inference: (a) listen-only discovery on the port will show nothing unless a tester is active, so the design must poll actively with 0x22; (b) measure pins 6-14 (truck asleep, multimeter) before deciding whether to enable an adapter's 120 Ω terminator. With roughly 120 Ω measured, adding a 120 Ω terminator gives a correct 60 Ω bus; with roughly 60 Ω, leave it off. Gateway reads (0x22) work without authentication per hw-4. Writes and programming need GM SDAC/MDI2 and are out of scope.
Sources: https://diag.net/msg/m1f2v9xm5s4xp8agm94j4c0t3i https://gm-techlink.com/wp-content/uploads/2021/04/GM_TechLink_06_Mid-March_2021.pdf https://stmobileauto.com/2026/04/23/gm-global-b-vip-architecture-module-programming-guide/

### [hw-6] (medium, CRITICAL) GM BT1 addressing needs custom 29-bit headers, a custom receive filter and user-defined ISO-TP flow control, and sources disagree on the exact IDs. The adapter must expose these controls.
VERIFIED as published configurations, but the correct IDs still need checking on the truck. WiCAN bt1.json: init 'ATST96;' then 'ATSP7;ATCP14;ATSHDACBF1;ATCRA142AF1CB;ATFCSH14DACBF1;ATFCSD300000;ATFCSM1;' for 2227C6. WiCAN sierra-ev.json: 'ATSP6;ATST64;' plus 'ATSH14DACBF1;ATCRA142AF1CB;'. OBDb chevrolet.json: 125 commands with hdr DA11, pri 14, rax 2AF111 and fcm1:true; also DA18 to 2AF118 and DA28 to 2AF128. Coldarn instead uses the default priority (ATSH DACBF1, i.e. 0x18DACBF1) with default receive filtering. Its clone rejected 4-byte ATSH, and it avoids 22 2B43 because the BEC 'emits a malformed ISO-TP length'. Inference: request 0x14DA<ecu>F1 with response 0x142AF1<ecu> appears to be GM-specific (non-standard PF 0x2A), with 0x18DA<ecu>F1 to 0x18DAF1<ecu> also accepted. The STN command manual (FRPM, Oct 2025) supports ATCP, ATCRA, ATFCSH, ATFCSD, ATFCSM, STCFCPA (flow-control address pairs), STCAF and STPX. comma panda's 'elm327' safety mode only allows sends to 0x18DB33F1, 0x18DA00F1 masked, 0x6xx/0x7xx and 0x24B, so it would block 0x14-priority requests.

## RECOMMENDATIONS
- Drop adb from the plan. The laptop is for building, CAN discovery and temporary bridging only. Deliver the dashboard app as an .aab through Play Console > Testing > Internal testing, with the user's Google account as tester, installed from the truck's Play Store. Build arm64-v8a or ABI-neutral, targetSdk 34, minSdk 32. Test on GM's Lyriq emulator image by adding the SDK update site https://developer.gm.com/v1/android-emulator/repository.xml in Android Studio > SDK Manager > SDK Update Sites.
- Before buying much hardware, open Play Console > Device catalog, filter Form factor = Car and manufacturer GM, find the Silverado EV / VCU head-unit entry, and record its System features (android.hardware.bluetooth_le, android.hardware.usb.host, android.hardware.wifi) and ABIs.
- Ship a small 'connectivity probe' app first through internal testing (no vehicle data; parked use only). It should: (a) BLE-scan and connect to an OBDLink CX and send 'ATI' and 'STI'; (b) list UsbManager devices and open an FTDI/CDC device; (c) open a WifiNetworkSpecifier local-only link to the laptop's hotspot (exact SSID+BSSID) and fetch a test page. The results choose the transport: BLE first, then USB-serial, then Wi-Fi.
- Hardware to buy now: OBDLink CX (BLE, STN2310, <1 mA sleep) for the head-unit path; OBDLink EX (USB, STN2232) or MX+ for laptop scripting with pyserial/rfcomm; and one SocketCAN interface. Prefer PEAK PCAN-USB FD (CAN FD, isolated, mainline peak_usb); a CANable 2.0 is enough for classic CAN only. Add a CiA 303-1-pinout OBD-to-DB9 cable (check with a meter: DB9 7 = CAN_H to OBD 6, DB9 2 = CAN_L to OBD 14, DB9 3 = GND to OBD 5). WiCAN Pro is optional if Wi-Fi or Home Assistant is wanted.
- Install on the laptop: `sudo pacman -S python-can python-pyserial python-bleak bluez-deprecated-tools`, then from the AUR (paru/yay) `can-utils python-can-isotp python-udsoncan savvycan python-cantools android-studio`. The kernel modules (can-isotp, peak_usb, gs_usb, kvaser_usb, slcan) are already present in the 7.2.10-cachyos kernel.
- Laptop discovery procedure (read-only): (1) with the truck asleep, measure resistance across OBD pins 6-14 to decide on termination; (2) bring can0 up listen-only at 500 kbit/s and confirm the port is quiet and error-free; (3) switch to normal mode and send only single-frame `22 xx xx` requests to BEC 0xCB and DMCM 0x17. Try both 14DACBF1↔142AF1CB and 18DACBF1↔18DAF1CB through can-isotp. Record everything with `candump -l any`. (4) Rate-limit to 10-20 requests/s, use one tester at a time, and stop when the truck goes to sleep.
- Enforce a hard send whitelist in every tool (laptop scripts, bridge firmware, app): only UDS 0x22 (ReadDataByIdentifier), OBD 0x01/0x09, and optionally 0x19 read-DTC, to a fixed list of ECU addresses. Never send 0x10, 0x11, 0x14, 0x27, 0x28, 0x2E, 0x2F, 0x31, 0x34-0x37, 0x3D or 0x85. Do not try CAN FD sends unless classic CAN demonstrably fails.
- Only poll while the truck is awake, gated on 12 V voltage (ATRV/STN or the bridge's ADC) or an on/off signal, with an inactivity timeout. Configure STN STSLVL/STSLVLS or WiCAN sleep thresholds. Mount the dongle on a short (30 cm or less) low-profile right-angle OBD extension routed away from the pedals and lower-dash panels. Unplug for long-term parking until power draw has been measured.
- Architecture: MVP = AAOS app ↔ BLE ↔ OBDLink CX, doing ISO-TP and decoding in the app. If BLE is blocked, use an OBDLink EX through usb-serial-for-android (FTDI/CDC); failing that, a Wi-Fi bridge (WiCAN Pro TCP 3333, or a Pi/ESP32 WebSocket) joined with an exact-SSID WifiNetworkSpecifier. Phase 2 = ESP32-S3 + MCP2518FD bridge (start from bri3d/esp32-isotp-ble-bridge) that adds CAN FD capability, the send whitelist, awake gating and a compact BLE GATT data stream. Prototype the bridge on the laptop first: SocketCAN plus a Python BlueZ GATT server or a WebSocket on a laptop hotspot.
- Keep a fallback ready: Car Scanner Pro on a phone or tablet with an OBDLink MX+/CX already reads per-module voltages and temperatures on Silverado EVs, which is useful for checking your own decoded values. A WebView-shell AAOS app showing a bridge-served HTML dashboard is the quickest UI path if native UI work becomes a bottleneck.
