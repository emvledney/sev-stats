# gm-platform

## SUMMARY
Verified: the Silverado EV's infotainment ECU is GM's "VCU (Virtual Cockpit Unit)", RPO IVD/IVE. NHTSA bulletins show it runs the same radio software line as the Lyriq and Blazer EV, for example W27E-172.5.1-M169-SQBR4-126.1. Independent teardowns of the same GM Global-B Qualcomm radio (Lyriq/CT5) identify a Qualcomm Snapdragon SA8155P (arm64). It runs a QNX hypervisor that owns the safety-critical cluster, cameras and lights, with AAOS plus Google Automotive Services running as a guest VM. The 2024–2025 EVs shipped on Android 12L-based builds (SQBRx: SQBR3→SQBR4→SQBR5→SQBR6; SQBR6 is dealer-installed and ships on 2026 trucks). The Android 14 build (UQBM) is rolling out through dealers and now OTA: for the 2024 Silverado/Sierra EV it is "GM Update 662.30", whose release notes say "Improvements to the infotainment system from Android update". Developer Options can sometimes be toggled on GM EV units, but ADB does not work on production units. GM gates ADB behind its own authentication. The in-cab USB-C/A ports are host ports behind a bridge chip, and wireless debugging is never reachable. So the plan cannot rely on `adb install` from the laptop. USB-stick APK sideloading through a file-manager trick worked on early builds but is reported closed on SQBR6/UQBM. Sideloaded apps are also always blocked while driving, because AOSP CarPackageManagerService only honors distractionOptimized for apps whose installer is an allowed store. The working, non-invasive route, used by many owners on Silverado EV, Sierra EV, Blazer EV, Equinox EV, Optiq and CT5 in 2025–2026 including Android 14, is the user's own Google Play Console app. It goes on the dedicated Android Automotive OS track → Internal testing (no form-factor review), with the truck's Play Store Google account as the tester, and is installed by picking the truck in the Play web install dialog. GM's developer portal (developer.gm.com) now offers only (1) B2B cloud "API & Data Services" that need a commercial agreement and (2) a public Android Studio SDK update site with GM emulator images (Cadillac LYRIQ and CELESTIQ, API 34 x86_64, "VCU1.0/Android14"). There is no Silverado EV image, no consumer vehicle-data SDK and no sideload program. For vehicle data, an ordinary Play-installed app can read only standard VHAL properties. A real GM EV exposes INFO_EV_BATTERY_CAPACITY, EV_BATTERY_LEVEL, RANGE_REMAINING, EV_BATTERY_INSTANTANEOUS_CHARGE_RATE, the charge-port flags and ENV_OUTSIDE_TEMPERATURE, through CAR_INFO (install-time) and CAR_ENERGY (runtime-granted on GM Android 14). EV_CURRENT_BATTERY_CAPACITY and odometer (CAR_MILEAGE) are not available, and nothing like cell voltages, pack V/I or Ah exists in VHAL. So the cell-level parts of the dashboard must come from an external read-only interface feeding the app. GM AAOS does let ordinary apps use USB host devices (UsbManager, with two permission prompts on every connect), USB Ethernet adapters (an eth0 shows up), Bluetooth, and sockets on the car-hotspot interface (ap_br_swlan0). These are the realistic data paths. Ultium EVs other than the Lyriq do not support CarPlay or Android Auto in the US; the 2024–25 Silverado EV WT trim was an exception with an 11-inch screen. Chrome and YouTube are available from GM's curated Play Store for parked use only. Engineering access paths exist only as exploits (EEPROM/UART mods, GM-private ADB binders, unprotected com.gm.vehicleinfo providers, SPS/BCM calibration flips). They carry brick and warranty risk, can be reverted by an update (firmware downgrades are impossible), and GM has acted legally against a modder (WAMS). None should be used.

### [gm-2] (high, CRITICAL) ADB (USB or Wi-Fi/wireless debugging) is not usable on production GM EV head units, so `adb install` / `adb logcat` from the laptop is not available. The in-cab USB ports act as host ports.
Owner reports: on a 2025 Equinox EV (XDA slyosx, 2025-09-27) ADB could not be enabled over USB or Wi-Fi. On a Cadillac Optiq, Dev Mode and USB debugging were enabled but there was still no ADB. On an Equinox EV (JTech, May 2026) Developer Options and USB debugging stay on, but the USB-C console ports give 'no adb access'. On another GM Android 14 unit USB debugging switches itself off. Developer mode can sometimes be triggered (a 2025 Sierra EV report, 2025-12-22). OpenAutoLink's on-car probe of a Blazer EV found adbd running and sys.usb.config=mtp,adb on controller a800000.dwc3. However, the user-facing ports sit behind a USB bridge-chip hub that stays in host mode, and turning on device-mode ADB goes through a GM-private binder (com.gm.server.screenprojection.RDMSADBHandler) and vendor.gm.* properties that ordinary apps cannot use. On the Intel gminfo3.7 ICE radio, GM uses certificate-based 'GM ADB' authentication, plus a 'dabridge' H2H bridge (USB VID 0x2996, PID 0x0100–0x0105) present only on specific receptacles. Owners report adb-wifi is never detected because the radio uses several internal VLANs. Consequence for the plan: the laptop is used to build and upload AABs, to run emulators, and optionally as a data source or log sink over the network. It cannot be a debugger attached to the head unit. In-app logging/export must be built in.

The cell-level and pack-electrical goals therefore need a separate read-only data source (another workstream). Never call CarPropertyManager.setProperty, to keep the 'no truck impact' rule.

## OPEN QUESTIONS
- Which trim (WT vs LT/RST/Trail Boss) and which build (Settings > System > About: SQBR5/SQBR6 vs UQBM) is on the user's truck? The WT used a different 11-inch screen with CarPlay/AA and may be a different radio, possibly the Intel gminfo.
- Has the user's 2024 truck already received GM OTA 'Update 662.30' (the Android update)? This decides whether to test against API 32 or API 34 first.
- The exact pixel resolution, density, and curved-edge cutout of the Silverado EV 17.7-inch panel are not published. They need to be measured in-app with WindowMetrics/DisplayMetrics, or taken from the GM Lyriq hardware profile as an approximation.
- Does the Silverado EV VHAL return values for EV_BATTERY_AVERAGE_TEMPERATURE, EV_BATTERY_INSTANTANEOUS_CHARGE_RATE while driving or charging, ENV_OUTSIDE_TEMPERATURE, and HVAC temperatures for a third-party app? So far this is only confirmed on a Blazer EV.
- Can a laptop or Pi joined to the truck's Wi-Fi hotspot open a TCP connection to a socket owned by the user's app (client isolation)? Does the hotspot AP work without an active OnStar data plan?
- Will GM AAOS let a third-party app act as a BLE GATT central to an OBD/BLE dongle? Will it enumerate CDC-ACM/FTDI USB-serial devices for UsbManager access?
- Does Play enforce the AAOS target-API (35) requirement on internal-testing uploads, or only on production?
- Could a future GM OTA restrict Play internal-test installs or DO for non-curated packages? There is no evidence of this as of 2026-10.

## RECOMMENDATIONS
- At the truck, read Settings > System > About and record the build string (SQBRx or UQBM), the Android version and the trim. Also note whether 'Update 662.30' has been applied. Do not toggle Developer Options; it gives nothing useful and only adds risk.
- Drop the 'adb install from a connected laptop' assumption. The laptop's roles are: build and sign AABs, upload them to Play Console, run AAOS emulators, and optionally serve as a read-only data source or log sink over the truck hotspot or a USB-Ethernet dongle.
- On CachyOS, install Android Studio and the SDK. Add the GM SDK Update Site https://developer.gm.com/v1/android-emulator/repository.xml and install the LYRIQ API 34 image. Also install the generic 'Android Automotive with Google APIs' API 34-ext9 and 35 images, using no-Play images for distraction-optimization testing. Create a custom Automotive hardware profile approximating a 17.7-inch landscape screen (resolution TBD).
- Play Console setup: verify the personal developer account (an Android device is required for verification). Create the app, add the Android Automotive OS form factor with a dedicated track, and upload to Internal testing (AAOS). Add the truck's Play-store Google account as a tester, join through the web link, and install by choosing the truck in the Play web device picker. Keep the applicationId and upload key permanent, and increment versionCode on every release.
- Build an ABI-agnostic Kotlin/Compose app with no native libraries, minSdk 32 and targetSdk 35. Declare <uses-feature android:name="android.hardware.type.automotive" android:required="true"/> and request CAR_INFO, CAR_ENERGY, CAR_ENERGY_PORTS, CAR_EXTERIOR_ENVIRONMENT, CAR_POWERTRAIN and CAR_SPEED. Ask the user to grant CAR_ENERGY and CAR_SPEED under Settings > Apps > [app] > Permissions. Use CarPropertyManager subscribe and read calls only; never call setProperty or any write API.
- Treat VHAL as the source only for SoC, energy (Wh), capacity (Wh), range, charge rate and charge-port state. Plan a separate read-only external acquisition path for pack V/I, cell voltages, temperatures and Ah, via a BLE dongle, a USB device, or TCP from a laptop/Pi. That path feeds the app over UsbManager, BluetoothGatt, or a socket on ap_br_swlan0 or eth0 (another workstream covers which bus data and DIDs to read).
- Design for driver distraction. Mark only a minimal glance screen as distractionOptimized; it only takes effect because the app is Play-installed. Show detailed cell grids and charts only when CarUxRestrictionsManager reports unrestricted (Park). Respect display-cutout and system-bar insets for the curved RST screen.
- Because there is no logcat, build in an on-screen diagnostics page (VHAL property status, permission status, connection status), plus log export to a FAT32 USB stick or an HTTP POST to the laptop on the hotspot.
- Do not use exploits, community-extracted GM firmware or emulators, unprotected com.gm.vehicleinfo providers, SPS/DPS reflashing, BCM calibration edits, EEPROM/UART mods, or USB-stick APK sideloading. They risk bricking the radio, cannot be rolled back, may void warranty, breach GM and Play terms, and may affect safety displays.
- After every GM OTA or dealer update, re-test install, permissions and Bluetooth pairing. Owners report that the Android 14 updates reset Bluetooth and closed the sideload path.
